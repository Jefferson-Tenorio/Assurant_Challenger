Como Arquiteto de Dados Sênior, não começamos criando tabelas aleatoriamente. Começamos definindo **Domínios de Dados** e **Padrões de Acesso**.

Para o seu desafio da Assurant (Seguros), temos 3 desafios mortais de modelagem:
1.  **Viagem no Tempo:** O contrato muda, o sinistro é retroativo.
2.  **Segurança (LGPD):** Precisamos deletar dados pessoais sem quebrar a integridade financeira.
3.  **Escala:** O Postgres não pode guardar tudo.

Aqui está a **Modelagem Lógica e Física (Script DBA)** para a **Etapa 1**, focada no PostgreSQL (Core).

### Estratégia Macro: O Padrão "Vault" e "Temporal Validity"

Vamos separar os dados em Schemas para organização e segurança:
*   `access`: Controle de acesso e PII (Personal Identifiable Information). **Aqui mora a LGPD.**
*   `core`: O coração do negócio (Apólices, Coberturas). **Aqui mora a validade temporal.**
*   `finance`: Sinistros e Pagamentos. **Aqui mora o dinheiro.**

### 1. O "Cofre" de Dados Pessoais (LGPD Friendly)
**Conceito:** *Crypto-Shredding Pattern*.
Nunca espalhe o CPF/Nome do cliente por 50 tabelas. Crie uma tabela central. Todas as outras tabelas usam apenas o `customer_id` (UUID). Se o cliente pedir para ser esquecido, você apaga/anonimiza **uma linha** aqui e o resto do banco vira dados anônimos históricos para Analytics.

```sql
-- Habilitar extensões necessárias
CREATE EXTENSION IF NOT EXISTS "uuid-ossp";
CREATE EXTENSION IF NOT EXISTS "btree_gist"; -- Vital para constraints temporais

CREATE SCHEMA access;

CREATE TABLE access.customers_pii (
    customer_id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    full_name VARCHAR(255) NOT NULL,
    tax_id VARCHAR(50) NOT NULL, -- CPF/CNPJ/SSN
    email VARCHAR(255) NOT NULL,
    phone_encrypted TEXT NOT NULL, -- Exemplo de campo criptografado na app
    
    -- Metadados de Auditoria
    created_at TIMESTAMPTZ DEFAULT NOW(),
    updated_at TIMESTAMPTZ DEFAULT NOW(),
    
    -- Controle de Exclusão Lógica (Soft Delete)
    deleted_at TIMESTAMPTZ NULL, 
    
    -- Constraint para garantir unicidade do documento apenas se não estiver deletado
    CONSTRAINT unique_tax_id_active UNIQUE NULLS NOT DISTINCT (tax_id, deleted_at)
);

-- Índices para busca rápida
CREATE INDEX idx_customers_email ON access.customers_pii(email) WHERE deleted_at IS NULL;
```

### 2. O Core: Apólices com "Viagem no Tempo" (Temporal Validity)
**Conceito:** *Validity Range*.
Aqui resolvemos o problema: "Dia 01 tinha cobertura, Dia 02 tirou, Dia 03 reclamou sinistro do dia 01".
Não vamos sobrescrever o registro (UPDATE). Vamos versionar.

Usaremos o tipo `tstzrange` (Range de Timestamp com Timezone) do PostgreSQL. É uma arma secreta de DBAs.

```sql
CREATE SCHEMA core;

CREATE TABLE core.policies (
    policy_id UUID DEFAULT uuid_generate_v4(),
    policy_number VARCHAR(50) NOT NULL, -- O número legível no papel
    customer_id UUID NOT NULL REFERENCES access.customers_pii(customer_id),
    
    -- O período de validade DESTA VERSÃO da apólice
    -- Ex: '[2024-01-01 10:00, 2024-06-01 10:00)'
    validity_period tstzrange NOT NULL,
    
    status VARCHAR(20) CHECK (status IN ('ACTIVE', 'SUSPENDED', 'CANCELLED')),
    product_code VARCHAR(50) NOT NULL,
    
    -- Dados JSONB para flexibilidade de produtos diferentes (Carro vs Casa)
    risk_attributes JSONB NOT NULL, 
    
    -- Constraints Poderosas
    -- EXCLUDE: Garante que não existam duas versões da MESMA apólice se sobrepondo no tempo.
    -- Isso impede o erro lógico de ter dois status ativos ao mesmo tempo.
    EXCLUDE USING GIST (
        policy_number WITH =, 
        validity_period WITH &&
    )
);

-- Tabela de Coberturas (Detalhe)
-- Também temporal, pois posso remover a cobertura de "Vidros" no meio do contrato
CREATE TABLE core.policy_coverages (
    coverage_id UUID DEFAULT uuid_generate_v4(),
    policy_id UUID NOT NULL, -- Aqui não usamos FK simples, explicarei abaixo
    coverage_type VARCHAR(50) NOT NULL, -- 'GLASS', 'THEFT', 'FIRE'
    limit_amount DECIMAL(15,2) NOT NULL,
    deductible_amount DECIMAL(15,2) NOT NULL, -- Franquia
    
    validity_period tstzrange NOT NULL,
    
    -- A cobertura deve estar contida no tempo da apólice? 
    -- Complexo validar via SQL puro, geralmente validado na App.
    
    EXCLUDE USING GIST (
        policy_id WITH =,
        coverage_type WITH =,
        validity_period WITH &&
    )
);
```

**Como funciona a query de "Viagem no Tempo"?**
Se o sinistro ocorreu em `2024-02-15`:
```sql
SELECT * FROM core.policy_coverages 
WHERE policy_id = '...' 
  AND coverage_type = 'GLASS'
  AND validity_period @> '2024-02-15 14:00:00+00'::timestamptz;
-- O operador @> significa "Contém". O banco acha a versão exata daquele milissegundo.
```

### 3. Financeiro: Sinistros (Imutabilidade)
**Conceito:** O sinistro aponta para o passado.

```sql
CREATE SCHEMA finance;

CREATE TABLE finance.claims (
    claim_id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    policy_number VARCHAR(50) NOT NULL, -- Referência humana
    customer_id UUID NOT NULL,
    
    incident_date TIMESTAMPTZ NOT NULL, -- A data DO FATO (que define a cobertura)
    reported_date TIMESTAMPTZ DEFAULT NOW(), -- A data que avisaram
    
    status VARCHAR(20) DEFAULT 'OPEN',
    estimated_loss DECIMAL(15,2),
    approved_amount DECIMAL(15,2),
    
    rejection_reason TEXT,
    
    -- Particionamento: Sinistros são dados que crescem muito.
    -- Vamos particionar por Data de Report (Range).
    -- Nota: A chave primária precisa incluir a coluna de partição.
    CONSTRAINT pk_claims PRIMARY KEY (claim_id, reported_date)
) PARTITION BY RANGE (reported_date);

-- Criando partições (Automação via pg_partman idealmente)
CREATE TABLE finance.claims_y2024m01 PARTITION OF finance.claims
    FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');
```

### 4. Modelo NoSQL (Cassandra) - Telemetry & Logs
Para o Cassandra, esquecemos formas normais. Modelamos para a pergunta:
*"Quero ver todo o histórico de condução/eventos da Apólice X ordenado por tempo."*

```sql
-- Keyspace
CREATE KEYSPACE insurance_telemetry 
WITH replication = {'class': 'NetworkTopologyStrategy', 'us-east': 3, 'sa-east': 3};

-- Tabela de Eventos de Telemetria (IoT)
CREATE TABLE insurance_telemetry.policy_events (
    policy_id UUID,
    event_time TIMESTAMP,
    event_type TEXT, -- 'BRAKING', 'ACCELERATION', 'GPS_PING'
    metadata MAP<TEXT, TEXT>, -- Flexibilidade: {'speed': '120', 'lat': '-23.5'}
    
    -- Chave Primária Composta
    -- policy_id = Partition Key (Distribui os dados pelo cluster)
    -- event_time = Clustering Key (Ordena os dados no disco)
    PRIMARY KEY ((policy_id), event_time)
) WITH CLUSTERING ORDER BY (event_time DESC);
-- Isso torna a leitura dos "últimos eventos" absurdamente rápida.
```

### Por que modelamos assim? (Justificativa para o Desafio)

1.  **UUIDs em tudo:** Como temos regiões BR e US isoladas, se usássemos `SERIAL` (1, 2, 3), teríamos colisão de IDs quando jogássemos os dados no Data Lake global. UUID garante unicidade universal.
2.  **Schema `access` isolado:** Facilita auditoria. Podemos colocar regras de criptografia mais pesadas apenas nesse schema.
3.  **Temporal Tables (`tstzrange`):** Resolve o requisito complexo de "histórico de apólices" sem precisar criar tabelas de `_history` manuais gigantescas e complexas de consultar. O Postgres faz a matemática de intervalo para nós.
4.  **NoSQL Query-Driven:** No Cassandra, a tabela é desenhada para suportar a tela de "Detalhes da Viagem" do App, sem JOINS.

### 1. A Trilha de Auditoria Imutável (Topic 7: Immutable audit trails)
O desafio pede explicitamente: *"registram quem, quando e o que"*.
As colunas `created_at` e `updated_at` na tabela principal **não são auditoria**, são metadados de estado atual. Se eu mudar o valor da apólice de 100 para 200 e depois para 300, o `updated_at` só mostra a última mudança. Eu perdi a mudança intermediária.

**A Solução (SQL):** Adicionar uma tabela de Auditoria Centralizada (Pattern: *Audit Log Table*).

```sql
CREATE SCHEMA audit;

-- Tabela imutável (Append-Only)
CREATE TABLE audit.change_logs (
    log_id UUID DEFAULT uuid_generate_v4(),
    table_name VARCHAR(50) NOT NULL,
    record_id UUID NOT NULL,
    operation VARCHAR(10) NOT NULL, -- INSERT, UPDATE, DELETE
    changed_by VARCHAR(100) NOT NULL, -- Usuário da Aplicação ou DB User
    changed_at TIMESTAMPTZ DEFAULT NOW(),
    
    -- O "Pulo do Gato": Guardar o estado ANTES e DEPOIS em JSON
    old_values JSONB, 
    new_values JSONB,
    
    -- Particionamento por Mês é OBRIGATÓRIO aqui (cresce muito rápido)
    PRIMARY KEY (log_id, changed_at)
) PARTITION BY RANGE (changed_at);

-- Exemplo de partição
CREATE TABLE audit.change_logs_y2024m01 PARTITION OF audit.change_logs
    FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');

-- Como preencher isso?
-- Opção Junior: Código da aplicação insere. (Inseguro, se alguém rodar update no banco, não gera log)
-- Opção Senior: Triggers de Banco de Dados.
```

### 2. Controle de Concorrência Otimista (Topic 4: Transaction Coordination)
O desafio fala de sistemas distribuídos. Imagine que dois corretores abrem a mesma apólice ao mesmo tempo para editar.
1.  Corretor A lê versão 1.
2.  Corretor B lê versão 1.
3.  Corretor A salva versão 2.
4.  Corretor B salva versão 2 (e sobrescreve o trabalho do A). **Isso se chama "Lost Update"**.

**A Solução:** Adicionar uma coluna de versionamento na tabela `policies`.

```sql
ALTER TABLE core.policies ADD COLUMN version_id BIGINT DEFAULT 1;
```

*   **Na Query de Update:**
    ```sql
    UPDATE core.policies 
    SET status = 'CANCELLED', version_id = version_id + 1
    WHERE policy_id = '...' AND version_id = 1; -- Se alguém mudou pra 2 antes, isso retorna 0 linhas.
    ```
Isso garante consistência sem travar o banco (Lock).

### 3. A Conexão Explícita "Sinistro vs Versão da Apólice" (Topic 6)
No modelo anterior, o link era lógico. Vamos torná-lo mais robusto para performance.
O sinistro não acontece na apólice "hoje". Ele acontece numa "foto" da apólice no passado.

Não precisamos mudar a tabela, mas precisamos garantir o **Índice** que faz essa busca ser rápida.

**O Problema de Performance:**
Fazer join de `claims` com `policies` usando `tstzrange` (`validity_period @> incident_date`) é pesado computacionalmente se a tabela for gigante.

**A Solução (Otimização GiST):**
Certifique-se de que o índice na tabela `policies` suporta essa busca temporal.

```sql
-- Índice GiST para acelerar buscas de "Quem estava ativo nesta data?"
CREATE INDEX idx_policies_validity ON core.policies USING GIST (validity_period);
-- Sem esse índice, o relatório de sinistros vai fazer Full Table Scan e derrubar o banco.
```

### 1. A Revisão Incansável (O que ainda falta?)

#### A. O Problema da Performance do UUID (Index Fragmentation)
**Crítica:** Usar `uuid_generate_v4()` (totalmente aleatório) como Chave Primária (PK) mata a performance do banco em inserções massivas. O índice B-Tree precisa se rebalancear o tempo todo porque os IDs não são sequenciais.
**Correção:** Adotar o padrão **UUIDv7** (Time-Sorted UUID). Ele é sequencial baseada no tempo, mas ainda único globalmente. Isso mantém o índice B-Tree saudável e rápido.
*   *Obs:* Como o Postgres nativo (antes do v17) não gera v7 nativamente, geramos na **Aplicação** ou via função customizada, mas o tipo no banco continua `UUID`.

#### B. A Falha da Idempotência (Network Flukes)
**Crítica:** O desafio pede "Transaction Coordination Without Global Locks" (Tópico 4). Se a API mandar criar um sinistro, a rede falhar, e a API tentar de novo (retry), o banco vai criar dois sinistros duplicados?
**Correção:** Adicionar a coluna `idempotency_key` (UNIQUE) nas tabelas transacionais (`claims`, `policies`). O cliente envia um ID único da requisição. Se tentar reenviar, o banco bloqueia.

#### C. O Risco da Rotação de Chaves (Key Rotation - Security)
**Crítica:** Você criptografou os dados sensíveis (PII). Mas e se a chave vazar e você precisar trocar a chave mestre (Rotation)? Como você sabe qual linha foi encriptada com a chave velha (v1) e qual com a nova (v2)?
**Correção:** Adicionar a coluna `encryption_key_id` ou `key_version` nas tabelas que contêm dados criptografados.

#### D. Dinheiro Multi-Moeda (Internationalization)
**Crítica:** `DECIMAL(15,2)` assume que tudo é a mesma moeda. Em um sistema global, misturar Dólar com Iene (que não tem centavos) ou Real vai causar erro contábil.
**Correção:** Padrão **Composite Monetary Type**. Sempre guarde `amount` E `currency_code`.

### 2. O Schema Final "Blindado" (Com os Ajustes)

Aqui está o SQL refinado com esses ajustes finos aplicados:

```sql
-- 1. EXTENSÕES & DOMÍNIOS
CREATE EXTENSION IF NOT EXISTS "btree_gist"; 
-- UUIDv7 deve ser gerado pela aplicação, mas armazenamos como UUID.

-- Domínio para garantir consistência de moeda
CREATE TYPE currency_code_enum AS ENUM ('USD', 'BRL', 'EUR', 'GBP');

-- 2. SCHEMA DE ACESSO (CRYPTOSHREDDING + KEY ROTATION)
CREATE SCHEMA access;

CREATE TABLE access.customers_pii (
    customer_id UUID PRIMARY KEY, -- APP GERA UUIDv7
    
    -- Dados Criptografados na Aplicação (Ciphertext)
    full_name_encrypted BYTEA NOT NULL, 
    tax_id_encrypted BYTEA NOT NULL,
    
    -- Metadados de Criptografia (Vital para Key Rotation)
    key_version_id INT NOT NULL, -- Ex: 1, 2. Se for rodar rotação, a app sabe quem decriptar.
    
    -- Hash Blindado para Buscas (ex: SHA256 do CPF com Salt)
    -- Permite buscar "Quem é o CPF X?" sem decriptar o banco todo.
    tax_id_blind_index VARCHAR(64) NOT NULL,
    
    created_at TIMESTAMPTZ DEFAULT NOW(),
    deleted_at TIMESTAMPTZ NULL
);
CREATE UNIQUE INDEX idx_tax_blind ON access.customers_pii(tax_id_blind_index) WHERE deleted_at IS NULL;

-- 3. SCHEMA CORE (IDEMPOTÊNCIA + TEMPORAL)
CREATE SCHEMA core;

CREATE TABLE core.policies (
    policy_id UUID PRIMARY KEY, -- UUIDv7
    policy_number VARCHAR(50) NOT NULL,
    customer_id UUID NOT NULL REFERENCES access.customers_pii(customer_id),
    
    -- Controle de Concorrência
    idempotency_key VARCHAR(100), -- ID único da Requisição HTTP
    version_id BIGINT DEFAULT 1,  -- Optimistic Locking
    
    -- Temporalidade
    validity_period tstzrange NOT NULL,
    
    -- Dados flexíveis
    risk_attributes JSONB NOT NULL,
    
    EXCLUDE USING GIST (policy_number WITH =, validity_period WITH &&),
    CONSTRAINT uq_policy_idempotency UNIQUE (idempotency_key) -- Garante que retry não duplica
);

-- 4. SCHEMA FINANCEIRO (MULTI-CURRENCY)
CREATE SCHEMA finance;

CREATE TABLE finance.claims (
    claim_id UUID DEFAULT gen_random_uuid(),
    policy_id UUID NOT NULL, -- Link com a apólice (histórica é via query)
    
    -- Valores Monetários Compostos
    estimated_loss_amount DECIMAL(18,2),
    estimated_loss_currency currency_code_enum NOT NULL, -- USD/BRL
    
    incident_date TIMESTAMPTZ NOT NULL,
    created_at TIMESTAMPTZ DEFAULT NOW(),
    
    PRIMARY KEY (claim_id, created_at) -- Preparado para Particionamento
) PARTITION BY RANGE (created_at);
```

### 3. O Catálogo de Design Patterns Utilizados

Aqui está a lista técnica que você vai colocar na documentação. Cada linha desse SQL representa um padrão de engenharia de software consagrado.

#### Padrões de Dados e Integridade
1.  **Crypto-Shredding:** (*Tabela `access.customers_pii`*). Segregação de dados sensíveis para permitir "exclusão lógica segura" ao deletar apenas a chave ou o registro central, mantendo a integridade referencial do resto.
2.  **Bi-Temporal Modeling (Simulado):** (*Tabela `policies`*). Uso de `validity_period` (Valid Time) combinado com tabela de Auditoria (Transaction Time). Permite saber "O que era verdade no dia X" e "Quando soubemos que era verdade".
3.  **Optimistic Locking:** (*Coluna `version_id`*). Controle de concorrência sem travar o banco (Lock-free), prevenindo a anomalia "Lost Update".
4.  **Idempotency Key:** (*Coluna `idempotency_key`*). Garante que operações de escrita sejam processadas exatamente uma vez, mesmo com falhas de rede (Retry Storms).
5.  **Soft Delete:** (*Coluna `deleted_at`*). O dado nunca é apagado fisicamente imediatamente, permitindo recuperação e auditoria.
6.  **Schema Evolution / EAV (Entity-Attribute-Value) Moderno:** (*Coluna `JSONB`*). Permite adicionar campos novos (ex: "Modelo do Drone") sem alterar a estrutura rígida da tabela (ALTER TABLE).

#### Padrões de Arquitetura e Segurança
7.  **Cell-Based Architecture (Bulkheads):** (*Isolamento Físico BR/US*). Evita que uma falha catastrófica em uma região derrube o sistema global.
8.  **Shared-Nothing Architecture:** (*Clusters de DB separados*). Cada nó é independente, eliminando pontos únicos de falha (SPOF).
9.  **Defense in Depth:** (*Row Level Security + Encryption*). Segurança aplicada em camadas: Rede -> App -> Banco (RLS) -> Dado (Criptografia).
10. **Blind Indexing:** (*Coluna `tax_id_blind_index`*). Técnica para buscar dados criptografados sem precisar decriptar a tabela inteira (Performance + Segurança).

#### Padrões de Integração
11. **Transactional Outbox:** (*Setup do Debezium*). Garante consistência dual: "Só publico no Kafka se a transação no Postgres for commitada com sucesso".
12. **Polyglot Persistence:** Usar a ferramenta certa para o trabalho (Postgres para ACID, Cassandra para Escrita Massiva, ClickHouse para OLAP).

### Conclusão
Com essas revisões e essa lista de padrões, você não está apenas "criando um banco". Você está implementando uma **Arquitetura de Dados de Classe Enterprise**.

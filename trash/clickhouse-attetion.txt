Dicas de Especialista para o "Stress Test"
Você mencionou que o sistema será estressado. Aqui estão os pontos onde isso costuma falhar nessa arquitetura e como se prevenir:
Partições do Redpanda:
O gargalo geralmente não é o ClickHouse gravando, mas a velocidade de leitura do Kafka.
Ação: Ao criar o tópico insurance.sys.transactional_outbox no Redpanda, use pelo menos 3 partições.
Config: Se usar 3 partições, altere no SQL acima kafka_num_consumers = 3. O ClickHouse abrirá 3 threads de leitura simultâneas.
Deduplicação (ReplacingMergeTree):
A tabela ReplacingMergeTree não remove duplicatas imediatamente. Ela remove durante um processo chamado "merge", que acontece em background.
No Teste: Se você fizer um SELECT count() logo após a carga, pode ver números maiores que o esperado.
Solução: Para validar os dados precisos no final do teste, use SELECT ... FINAL ou OPTIMIZE TABLE insurance.outbox_analytics FINAL;.
Parsers JSON:
O comando JSONExtractString consome CPU. Se o container do ClickHouse bater 100% de CPU, o consumo da fila do Redpanda vai atrasar (lag).
Monitoramento: Fique de olho no log do ClickHouse. Se vir mensagens sobre kafka_max_block_size, significa que ele não está dando conta de processar o bloco antes de ler o próximo.
